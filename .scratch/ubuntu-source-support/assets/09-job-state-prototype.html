Reconnectable transcription job state

Drive the server-owned job registry through starts, progress, failures, disconnects, and a process restart, and watch what each browser client can recover. Changes no production code, stores nothing.

Which server-owned state machine and data contract should represent single-file, batch, and recording transcription jobs so every trusted browser client can recover progress, editable results, errors, and session-lifetime history — while live microphone capture ends with its capturing client and only durable files survive process restart?

Job registryThe local app session owns an ordered, session-lifetime list of jobs. Clients only render snapshots of it.
Statesqueued → running → completed | failed | cancelled. Recording adds capturing, bound to its capture client.
One at a timeOne job runs at a time; later starts queue behind it, whichever client submitted them.
RecoveryA reconnecting client gets the full registry: progress, editable results, errors, history — nothing is tab-local.
DurabilityProcess restart wipes the registry. Only saved output files (disk) survive.
