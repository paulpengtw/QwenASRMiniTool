Ubuntu browser lifecycle

Drive the local app process and its browser clients through launch, reconnect, failure, and shutdown. This prototype changes no production code and stores nothing.

Question this prototype answers Does it feel right for the local app process to own the loopback server while browser tabs remain disposable clients—so closing a tab does not silently kill work, relaunch reuses the running server, and only an explicit quit ends the app session?
Ready meansThe local UI/API responds; model loading is a separate state.
Close tabKeep the local app alive and allow a later reconnect.
RelaunchOpen the existing local app instead of starting a second server.
QuitUse an explicit UI action or terminal signal; confirm active work.
Open failurePrint the URL and keep listening for a manual browser connection.

Validated verdict

  • Session ownership: the process and loopback server own the local app session; tabs are disposable clients.
  • Readiness: UI/API readiness is independent from model readiness.
  • No clients: closing every tab leaves the app and non-recording jobs alive until explicit exit.
  • Recording: closing its capturing tab stops the microphone but retains completed segments for reconnection.
  • Relaunch: reuse a healthy session; replace stale ownership and start fresh when health fails.
  • Reconnect: recover server-owned job progress/results for the lifetime of the local app session.
  • Quit authority: every loopback client is trusted; destructive actions identify affected work and require confirmation.
  • Failure boundary: startup failures exit non-zero; model failures stay inside the ready UI.
  • Shutdown: notify clients, reject new work, cancel authorized work, stop child services, flush writes, then stop HTTP.
  • Bounded exit: allow 10 seconds, with forced second interrupt; use exit codes 0, 130, 143, or non-zero failure.
