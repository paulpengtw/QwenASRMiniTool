# Backend capability snapshot, effective backend, coded reasons rendered by the UI

Ticket: 05
Wave: B
Blocked by: 02, 03, 04, 06, 07
Status: open

Decision sources: 03 (read in full: capability states, effective vs preferred backend, no silent model switch, foreign paths, corrupt settings recovery, health only counts effective-backend blockers, navigation after readiness, the frontend never infers capability), 04 (codes + params), 06/08 (which features degrade).

Deliverables
- capabilities.py: build_snapshot(platform, settings_store, probes) -> dict. Backends: openvino_cpu (models 0.6B / 1.7B as backend-specific model choice), crispasr, chatllm_vulkan, cuda/pytorch as present in webview_backend today. Features: ffmpeg (video conversion + recording), cloudflared (tunnel), forced_alignment (use alignment_policy from ticket 07), diarization, endpoint. Each entry {state: ready|setup_required|machine_unavailable|platform_unsupported, reason: {code, params}|null, remedy: {code, params}|null, action: "download"|"install"|null}. Top level: backend_preference (persisted intent, possibly unsupported here, never overwritten), effective_backend + effective_model, status_line {code, params} (e.g. USING_OPENVINO_CPU_UBUNTU_PREF_PRESERVED when a Windows preference is preserved), model_state (unloaded|loading|ready|error + message), health {blockers: [...], optional: [...]} where blockers only include the effective backend and core workflows, recovery events (settings recovered -> SETTINGS_RECOVERED with backup path; session-ignored unhonourable values), and navigation hint {"target": "model"|"workspace"} per the readiness rule (missing prerequisites -> model; loading/ready -> workspace; load failure -> model with recovery actions).
- A fresh Ubuntu profile derives openvino_cpu + 0.6B; selecting 1.7B on Ubuntu writes the OpenVINO model choice under backends.openvino (shared) without touching the Windows backend preference. A missing/failed preferred model never switches silently: keep it selected, explain, offer an explicit switch action.
- API (webview_server.py + webview_backend.py): GET /api/capabilities returns the snapshot; /api/status embeds it under "capabilities"; GET /api/message-codes returns capability_codes.as_json(). Guard set_model / request_load so that a platform_unsupported choice is refused with a coded error and Windows binaries are never downloaded on Linux.
- Frontend: the model page renders ONLY from the snapshot: platform_unsupported choices do not appear in selectors; machine_unavailable are visible but disabled with reason + remedy; setup_required are selectable with an explicit download/setup action; Windows-only integrations live in a collapsed informational section "Not supported on Ubuntu / Ubuntu 不支援"; stable status line; recovery banners only when the snapshot carries a recovery event. i18n.js gains a renderCode(code, params) that uses the /api/message-codes table for the user's language (zh-TW/zh-CN map to "zh", en to "en"). Remove any frontend OS sniffing / filename-based capability inference you find.
Tests: tests/test_capabilities.py (linux fresh settings -> openvino_cpu 0.6B, preference untouched; Windows preference crispasr on linux -> preserved + status code; missing ffmpeg -> video/recording setup_required and NOT a blocker; missing model -> setup_required with download action; unhonourable values reported under recovery; health blockers rule), HTTP-level test of /api/capabilities and /api/message-codes against WebViewServer on an ephemeral port with a stub backend; a node --test for the pure JS "which control state to render" function (put it in webview/js/capability_view.js).
